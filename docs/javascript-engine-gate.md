Compiler rollout checks run the proposed compiler's JavaScript on **Node
22.22.1, Node 26.1.0 and installed Google Chrome**, independently. The required
`javascript-engine-rollout` CI job feeds `complete-conformance`; a failure,
missing engine or inconclusive measurement blocks that aggregate check.

Node 22.22.1 matches the audited application's pinned load-generator image.
It is a conservative compatibility target, **not an attestation of the hosted
Voyage server**. Node 26.1.0 is the audited development engine. Chrome is a real
browser process, driven through pinned Playwright Core; CI uses the runner's
installed Chrome, records its version and V8 revision, and fails if unavailable.
Safari, Firefox, production hardware, server capacity and frame rates are outside
this initial gate. Before a hosted rollout, identify that runtime and add its
actual engine/workload evidence; these local/CI checks cannot certify an unknown
server image.

From the distribution root, with the compiler already built:

```sh
npm ci --prefix tools/engine-gate --ignore-scripts --no-audit --no-fund
node tools/engine-gate/test.mjs
node tools/engine-gate/gate.mjs \
  --config bench/functionality/engine-gate/config.json \
  --compiler target/debug/ink --out build/engine-rollout \
  --node22 /absolute/path/to/node-22.22.1 \
  --node26 /absolute/path/to/node-26.1.0 \
  --chrome /absolute/path/to/google-chrome
```

The runner compiles into its output directory before timing. It never overwrites
application exports. Its frozen baseline was generated by distribution
`8bc7aae4dee9507c935783359d65bd7b7ad8949e`, JavaScript package
`626571d12ea525cac24a37bb197594e82e53cf1a`; source, artifact, adapter and compiler
binary hashes are recorded. The candidate is bound to its exact emitted bytes
and compiler binary; the tooling checkout and package pins are recorded separately.
Checkout metadata is provenance, not proof that a binary was built from it.

Each engine runs three fresh processes serially. Each case has at least 16,384
warmup calls, a 100 ms baseline warmup target, common calibrated batch sizes and
15 samples with alternating order. Setup, imports, independent result checking
and complete-output consumption are outside timed intervals. A separate
byte-identical baseline module supplies the A/A noise control. The public
corpus covers complete 8/100-element forecasts and sequential twelve-coordinate
gradient updates. An independent binary32 evaluator checks every forecast and
64 changing-weight updates; every timed batch's complete result is compared too.
These finite checks do not prove compiler correctness.

A case passes only when **every process** stays within the larger of **10% or
0.02 microseconds** of its own baseline median. A/A drift over 10%, or processes
that disagree about exceeding the budget, produce an inconclusive result, which
also blocks the gate. The budget tolerates small timing variation while detecting
the motivating 29% regression. Engines and cases are never averaged together.
Raw samples, process ratios and descriptive ranges remain available; they are
not statistical confidence intervals. Cold import times are recorded separately
and currently have no performance budget. Memory and whole-application latency
need separate evidence.

The baseline does not regenerate automatically. Updating it requires an explicit
review of source identities, hashes and per-engine results; a faster engine cannot
justify accepting a regression on another engine. The frozen floor is a regression
budget relative to that selected baseline, not a claim of zero change from every
preceding commit. Keep improvements' previous accepted artifacts when tightening
that floor.

Private applications can supply a private config and self-contained adapter with
`cases` (name, lifetime, create(module) -> complete call) and `verify(module)`
(independentChecks > 0). Config paths are relative to the config; `inputs` binds
all source/adapter dependencies, and `frozenHashes` protects the selected baseline
and controls. Keep application code and receipts in its private repository/audit
workspace. The loopback browser server exposes only declared adapter/artifact
files and the worker, rather than a repository directory.

Before promoting the tested candidate, recheck the receipt against its current
bytes, source inputs, compiler binary and unchanged measurement policy:

```sh
node tools/engine-gate/gate.mjs \
  --verify build/engine-rollout/receipt.json \
  --config bench/functionality/engine-gate/config.json \
  --candidate build/engine-rollout/candidate.mjs \
  --compiler target/debug/ink --out build/engine-rollout
```

The verifier recomputes the decision from raw measurements instead of trusting
the saved verdict. Stale artifacts, changed producer/tools/policy, incomplete
processes, missing verification or failed engine results reject. Receipts describe
their recorded host and engine identities; they are observations, not signed
certificates or authority to rewrite a program. `--candidate EXISTING.mjs` runs a
diagnostic comparison without compilation, and its receipt cannot be used for
promotion. Real app build/deployment systems must call the verifier before
replacing exports; this change wires the public corpus into Ink CI and does not
modify or deploy an external application.
