# Automatic boundary reader planning

Knowledge now proposes checked literal wire readers per pure function and transport format, individually and in combined module plans. The generic core checks exact source bindings, first-order interfaces, sorted unique sites and explicit target support. Backend code emits that choice; program names and JSON algorithms grant no applicability.

JavaScript's general synthetic usage profile now exercises trusted values, portable input/output and compact input/output. Encoded workloads also support recorded boundary operations. Selection measures validation, execution, output encoding and consumption of every reply byte; setup is recorded separately. Complete outputs and input ownership must validate in every acquisition process. These observations never replace source checking or prove backend correspondence.

An automatic smoke compilation of an unfamiliar two-field packet copier admitted four plans and generated 72 calls across all three boundaries without a workload file or handcrafted selection packet. The paired bootstrap guard selected both checked readers: estimated candidate/baseline lifecycle ratio 0.881, upper bound 0.930, 11 rounds and three comparisons. This is a single-process synthetic selection result on a shared host. It does not establish broad profitability, retained-memory savings or a Frontier win.

The selected package passed fresh proof replay and 48 independently generated encoded calls with exact complete replies and unchanged input bytes. Those holdout checks establish conformance for those inputs, not heldout performance. The first acquisition attempt is retained: it declined because the encoded target context was incorrectly compared with the trusted-call context. The mismatch was corrected before the successful acquisition.

Source, registry, every candidate, selected package, generated modules, raw receipt and checks are archived under artifacts/automatic-reader-selection. These are planning observations, not broad runtime profitability evidence. Complete context, records, receipts and funnel/near-miss attribution are in corpus/report.json and corpus/report.md.
