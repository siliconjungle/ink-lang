# Experimental native JSON ingress guard

The prototype uses native parsing only when native serialization equals every input character. Otherwise it falls back to the existing exact-token parser. Input byte/Unicode limits, source construction bounds, error classes/messages, duplicate rejection and exact bytes passed the retained conformance cases. Native prototype serializers disable the fast path.

This is an ignored experiment, not a published API, compiler rule, admitted database implementation or default.

Processes 290–292 bind the actual installed Frontier JavaScript files as well as its repository revision. Process 290 has a severe shared-host slowdown: its 512-field Frontier control takes 327.069 µs, versus 102.814 and 94.064 µs in the other processes. Its results are retained as diagnostic evidence, not a stable cost comparison.

At 512 fields in processes 291 and 292, guarded ingress/edit/direct-output takes 432.987 / 413.605 µs versus ordinary parse/capture/edit/direct-output 453.548 / 427.941 µs and existing direct-construction/edit/direct-output 493.182 / 475.268 µs. Guarded parsing itself does not consistently beat parse/capture, and small-input parsing often loses. These observations do not establish a robust lifecycle gain or an all-metrics win. Frontier's native JSON has different exact-token, ordering, validation and resource contracts.

Raw measurements, per-process medians, exact modules/plans/runner/prototype and conformance checks are retained. Repeated stable-host measurements would be required before extending the ABI or recording selectable cost evidence.
