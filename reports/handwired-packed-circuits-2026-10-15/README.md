# Packed circuits: first matched Handwired investigation

15 October 2026, Apple M4 Pro, macOS 15.7.4 arm64, Chrome 155 through the Codex
in-app browser. The first implemented and measured gains are search-focused.
This report does not establish general neural compilation, broad cross-domain
speedups, general regex support or a whole-compiler correctness proof.

## Resident searches

Complete non-overlapping literal counts on 100,000 documents generated by
Handwired `09f23d276d3b9284cea4eec61ffd934950cc979e`, seed 20261013 for development
and 20261015 held out. All characters are searched. Every document's count is
checked against independent native RegExp, before and after timed samples.

The table contains the median of three page medians, nine back-to-back samples
per page, in milliseconds. Pages share one browser process. Both GPU systems
retain inputs and return all 100,000 counts. Every timed call consumes all output;
parameter-table construction/upload and readback are inside the interval.

| Corpus | Literal | Handwired GPU | Earlier Ink DFA GPU | Packed Ink GPU | Ink JS before | Ink JS after | Native JS RegExp |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Development | error | 12.8 | 4.6 | 3.6 | 381.4 | 65.0 | 36.1 |
| Development | connection reset | 12.9 | 4.9 | 3.8 | 338.4 | 47.1 | 22.1 |
| Development | zzzzzzzz | 13.0 | 4.6 | 3.8 | 345.2 | 39.8 | 8.6 |
| Held out | error | 12.8 | 4.5 | 3.7 | 384.2 | 65.5 | 36.5 |
| Held out | connection reset | 13.5 | 5.1 | 3.8 | 346.4 | 46.8 | 22.4 |
| Held out | zzzzzzzz | 12.4 | 4.5 | 3.8 | 343.5 | 39.9 | 9.1 |

The packed implementation is 3.3–3.6 times faster than Handwired's public search
API here. It is about 1.2–1.3 times faster than Ink's explicit DFA under this
protocol. The JS change improves this pipeline by about 5.9–8.7 times, while
remaining slower than native JS search. Handwritten `indexOf` controls are also
retained in every receipt; they take 7.2–27.0 ms across these cases.

The earlier mixed CPU/GPU harness let long CPU calls interrupt GPU runs. Its
larger Ink GPU times cannot be attributed entirely to compiler or representation
changes: **the unchanged DFA also runs much faster in back-to-back blocks**.
Retaining it in this experiment distinguishes that protocol effect from packing.
No confidence interval or fresh-browser-process claim is made.

GPU temperature and scheduling materially change the numbers. All samples,
including slower Ink calls, are retained. At 100 documents, Ink GPU calls take

A 10,000-document control is retained too. These observations do not authorize
an automatic CPU/GPU choice without the normal comparable lifecycle evidence.

## Mechanisms and memory

The new ordinary `std:bit_automata` library uses a 32-bit Shift-And state and
small literal-mask tables. Inputs hold four mapped code points per u32 in
transposed storage, letting adjacent document invocations read adjacent words.
The earlier DFA uses one u32 per code point and a transition table. Both are
explicitly authored source algorithms, emitted literally by existing backends.

Per-session setup uploads fall from 205,216,420 bytes for the earlier Ink DFA to
51,601,068 bytes for packed Ink; packed live/peak buffers are 52,801,080 bytes in
the retained session counters. This is a comparison with the earlier Ink input
layout, not a whole-application memory comparison with Handwired.

Setup is retained separately. Median Handwired creation is 158.5/150.6 ms for
development/holdout; Ink DFA session opening is 103.1/91.6 ms; packed session
opening is 29.0/22.2 ms. These are **different component boundaries**: Ink engine
loading is excluded from session opening; the combined encoding timer constructs
both Ink representations; Handwired creation prepares its richer search and
highlighting machinery. These values do not establish an end-to-end first-call
win. An independent transfer-inclusive lifecycle comparison remains required.

## Native CPU and ownership

Three fresh processes per corpus, eleven paired alternating samples per process,
complete output checks against the same generated documents. New Rust lowering
`9ef76324` borrows lexical values for fixed read-only primitives. Milliseconds,
median of process medians:

| Corpus | Literal | Ink owning typed API | Handwritten borrowed Rust |
| --- | --- | ---: | ---: |
| Development | error | 31.776 | 9.527 |
| Development | connection reset | 35.366 | 15.391 |
| Development | zzzzzzzz | 23.971 | 4.690 |
| Held out | error | 31.369 | 9.604 |
| Held out | connection reset | 36.251 | 15.292 |
| Held out | zzzzzzzz | 25.441 | 4.692 |

Ink's typed API owns a `Vec<String>` and includes caller cloning in each timed
call. The handwritten control borrows strings and uses `str::match_indices`.
This measures those complete APIs/algorithms, not an isolated compiler ratio.
The new read-only primitive borrowing passes an allocation-counting mechanism
test, but produces little change in this whole-workload result. Broader ownership,
searcher reuse and prepared-call improvements remain substantive work.

## Correctness and scope

The benchmark maps non-octet code points to zero, excludes NUL patterns, rejects
documents beyond 512 code points and pads to that capacity. Each is a necessary
condition of this explicit encoding. Patterns are nonempty ASCII literals. Ink's
specialized literal algorithm has fewer capabilities than Handwired's regex
engine; it does not claim regex alternation, capture or leftmost-longest semantics.

The library has 128 independent cross-target cases, with 48 real eligible wgpu
calls, plus complete browser counts on both large corpora and size controls.
Eight checked scalar laws establish packed projections and bit-operation
components. They do not prove the whole matcher, source-to-packed conversion,
compiler, ABI, runtime or driver. No silent String replacement or automatic
selection was added.
