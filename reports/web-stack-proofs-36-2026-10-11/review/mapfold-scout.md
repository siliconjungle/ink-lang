# Batch36 map/fold scout

The proposed plain same-type arbitrary map→ordered right-fold fusion is already canonical. A complete pinned audit of snapshot b7d979fd… covers 2,508 objects and 1,702 semantic endpoint pairs; all four candidate endpoint pairs are alpha-equivalent to `web-stack/mapped_arbitrary_fold_{u32,i32,u64,f32}`. All twelve batch17 plain, mapped-prefix and mapped-concat arbitrary fold endpoints are present. Sixty-three canonical rewrite sources directly fold a mapped list. A renamed generic endpoint adds no novel search shape here.

The existing law has arbitrary pure total mapper f, arbitrary curried reducer g and arbitrary initial z. It preserves exactly `g(f(x0), g(f(x1), … z))`; g need not be associative or commutative. Old batch16 laws already cover arbitrary filtered/mapped ordered folds too. Fixed sum/subtraction/product laws are not the limit of the existing DB.

A newly bound source certificate could still be useful if an exact composed-helper source is not optimized by the ordinary full prior. That is a deployment/search issue, not a new generic theorem. Its novelty must be checked against the 63 mapped-fold source shapes, and helper/callee bodies must be content bound. Benchmark the unchanged prior planner before creating such certificates; source proof admission alone does not establish profitability.

Core semantic/checker typing currently requires the folded input element, initial accumulator, reducer arguments and output to be the same numeric type. Method map can change types, but fusing a type-changing map into a fold over its original differently typed list cannot be expressed using that current fold primitive. A general heterogeneous fold facility would be core machinery, with a separate semantic/backend justification.

Order is a substantive benchmark condition. The reference, Rust lowering and ordinary JS fold path traverse from the last element to the first. JS has a special replacement-tree path that can traverse forward for a restricted callback shape; it must not be assumed for an arbitrary order-sensitive reducer. Strong handwritten controls must retain right-fold direction, the original initial value, every mapper/reducer grouping and primitive wrapping. Empty input must return z. A forward fold, swapped reducer arguments, or reassociated F32 reduction is an invalid control. Accumulator-dependent branches, noncommutative operations and distinguishing short lists expose these mistakes.

The GPU ordered fold stage runs serially on gid.x=0 with a descending cursor; arbitrary order-sensitive reduction cannot simply become a parallel tree. A scalar fold's direct legacy shader is unsupported by the current array-result path, while an eligible literal graph can implement the ordered scalar reduction. Removing a materialized map could therefore remove one graph stage/buffer in some deployed source paths. That remains conditional on the exact named primary function and `graph_required` route, helper eligibility and actual dispatch/upload/readback/live-buffer measurements. Do not reuse batch35's legacy array-output counter formula for scalar folds. U64 generic correctness does not establish native U64 WGSL coverage; portable F32 WGSL does not promise exact CPU raw-bit equivalence.

Fusion reverses the mapper evaluation schedule relative to an eager forward map, while preserving values under total pure functions. Host effects, exceptions, callback counts and external mutation are outside that law. A proof preserves semantics, not cost: fusing loops may impair scalar/vector throughput, and full-call Wasm/GPU transport can dominate scalar reduction. Existing strong controls should already use one reverse loop without a mapped temporary. Preserve every regression and uncertain cell, and separate full-call from resident boundaries.

Conclusion: do not publish a duplicate generic map/fold law. A source-bound composition that the canonical prior misses could be promising, but needs a concrete prior gap, exact source novelty and measured gains. No new performance conclusion follows from this scout.
